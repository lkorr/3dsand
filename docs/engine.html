sandvox — engine architecture

A 3D falling-sand voxel engine: a GPU-resident cellular automaton over a 256³ world, raymarched directly from the simulation buffers. This page walks the per-tick pipeline stage by stage. Expand any stage for its mechanism, computation counts, and limits.

world 256³ = 16.7M voxels chunks 4096 × 16³ tick 30 Hz sim 0.25 ms active render 2.66 ms @1080p RTX 3060 Ti

Per-tick pipeline

Every tick runs these stages in order. The ordering is load-bearing: mutations must land before compaction (so newly-touched chunks are in the active set), and compaction must precede the CA passes (which dispatch indirectly off its output).

mutate→explode→compact→ 54 × CA→particles→occupancy→ readback→physics→render
▶ gpu MutationQueue All world writes — brush, explosions, island removal ≤64 ops

Every write to the world — brush strokes, explosions, worldgen, debris leaving the grid — enters through this queue and lands via sim_mutate.wgsl. Nothing else writes voxel memory.

This is the most important architectural rule in the engine, and it is not primarily about rendering correctness. The op stream is simultaneously the save format, the replay log, and the network replication stream. Because every mutation is captured here, recording the stream replays the world exactly.

Two op kinds

OpSizeCap / tickDispatch
BrushOp32 B64(4×ops, 4, 4) wg of 4³
CellOp8 B65,536(ops+63)/64 wg of 64

BrushOp is a radius-based sphere paint; CellOp writes one exact cell and is used by island removal, where the debris system must vacate precisely the voxels that became a rigidbody.

Computation

A brush op dispatches 64 workgroups of 64 threads = 4,096 threads per op, covering a 16³ box around the stroke. At the 64-op cap that is 262k threads, but typical interactive load is 1–2 ops per tick. Cell ops are one thread each — 65,536 threads at the cap.

Limits

Caps are per tick, not per second: a tool wanting more than 64 brush ops must spread them across ticks or batch into cell ops. Brush dispatch is sized for a 16³ box, so a radius above 8 voxels silently clips — the radius field is not validated against the dispatch size.

▶ gpu Explosions Ray-cast destruction, hardness budget, particle ejection ≤8 / tick

Two kernels, mark then apply. Rays cast from the blast center to every voxel on the blast sphere's surface, DDA-traversing outward and spending a hardness budget: harder material stops a ray, softer material is flagged for removal. A fraction of removed voxels eject as particles.

The key scaling property: ray count grows as O(r²) while destroyed volume grows as O(r³). Big explosions stay affordable because work tracks surface area, not volume.

Computation

Each op dispatches (11×n, 11, 11) workgroups of 4³ threads — 1,331 workgroups × 64 = 85,184 threads per explosion, covering the 44³ voxel box that bounds the max radius of 20. Both mark and apply pay this, so ~170k threads per explosion per tick. At the 8-op cap, ~1.4M threads.

Limits

Radius is hard-capped at 20 voxels (kMaxExplosionRadius); the dispatch geometry is sized for it at compile time, so raising the cap means changing EXP_WG in lockstep. Cost is paid for the full bounding box regardless of actual radius — a radius-2 explosion costs the same dispatch as radius-20.

▶ gpu Dirty compaction Scans 4096 chunk flags into a dense list + indirect args 64 wg

The stage that makes the whole engine scale. It scans the per-chunk dirty flags and compacts them into a dense index list, writing the workgroup count directly into an indirect-dispatch args buffer. The 54 CA passes then dispatch exactly one workgroup per dirty chunk — a settled world dispatches nothing.

This is what DESIGN.md §11 means by cost must scale with activity, not world size. Without it, every tick would dispatch over all 4,096 chunks whether or not anything moved.

Computation

4096 / 64 = 64 workgroups of 64 threads = 4,096 threads. This is a fixed cost paid every tick regardless of activity — negligible, and the reason the flat scan was chosen over DESIGN.md's hierarchical dirty tree, which only pays off at much larger residency.

Determinism note

List order is scheduling-dependent — it is built with atomicAdd append. This is safe because each dirty chunk appears exactly once and the color scheme makes all same-pass writes disjoint, so processing order cannot influence sim state. Order-dependence in the dispatch list is fine; order-dependence in a write would not be.

Limits

The flat scan is O(total chunks), not O(dirty chunks) — at 4,096 chunks it is free, but a much larger resident region would make the hierarchical tree worthwhile again.

▶ gpu Cellular automaton — 54 passes 27 color phases × 2 gravity substeps; movement + reactions 54 × dirty

The core simulation, and the largest single cost. Each tick runs 27 color phases × 2 gravity substeps = 54 indirect dispatches, each processing one workgroup of 6³ threads per dirty chunk.

Why 27 passes

Two threads must never claim the same destination cell, and the winner of any conflict must not depend on GPU scheduling — or the sim stops being reproducible, which kills lockstep networking and replay debugging.

The solution is a 3×3×3 cell-coloring lattice. Pass k updates only cells where (x%3, y%3, z%3) equals color k. Same-color cells are ≥3 apart on every axis, and movement reach is ≤1 cell, so destination writes are provably disjoint. The result is race-free and bit-deterministic with no atomics on voxel data.

Chunk-level checkerboarding — the 3D analog of Noita's 4-pass scheme — is not sufficient here, and this is a subtle trap. It makes simultaneously-updated chunks non-adjacent, but all 4,096 cells within a chunk still update in parallel on a GPU, so two movers in one chunk can collide. Noita never hits this because its CPU update is sequential inside each region.

The global-lattice invariant

The color lattice is global, not chunk-local. Because CHUNK = 16 ≡ 1 (mod 3), each chunk's first colored local coordinate shifts by its chunk coordinate. Dispatch must correct for this with start = (colorPhase + 3 - (chunkCoord % 3)) % 3. Omitting the correction produces a simulation that looks completely correct and is silently racy across chunk boundaries.

Computation

A 6³ workgroup = 216 threads covers a 16³ chunk's cells of one color (⌈16/3⌉³ = 6³). Per tick: 

54 dispatches × dirty_chunks workgroups × 216 threads
settled  (4 dirty):        ~46,700 thread-launches
moderate (200 dirty):     ~2.3M
heavy    (2000 dirty):    ~23.3M
all      (4096 dirty):    ~47.8M

Each cell is processed exactly once per substep, so total bandwidth is unchanged by the pass count — the 54 dispatches cost ~µs of launch overhead each, not 54× the work.

What each cell does

  • Stamp check — an 8-bit tick-stamp per voxel prevents a voxel that already moved from acting again in the same substep.
  • Reactions (substep 0 only) — scans the material's reaction bucket; pair, decay, and emit rules with tag matching.
  • Movement — powder falls then tries 4 down-diagonals; liquids add 4 lateral directions plus fullness equalization; gases invert.
  • Density displacement — a mover entering a lighter fluid swaps with it (sand sinks through water, oil floats).

All decisions use a stateless counter RNG, hash3(seed, tick, index) — never thread or dispatch order.

Limits

Write reach must stay ≤1 cell or the disjointness proof collapses. Everything influencing voxel state must be integer — floats diverge across vendors via FMA contraction and fast-math. Reaction-driven growth must be decisively subcritical: a rule averaging ≥1 offspring per tick means chunks never sleep, which presents as a performance bug but is a content bug.

▶ gpu Particle system Ballistic voxels in flight, DDA collision, claim-based reinsertion ≤262,144

When a voxel should fly — splash, explosion ejecta, rigidbody displacement — it leaves the grid and joins a GPU particle buffer carrying position, velocity, and its 16-bit voxel payload. This is what makes liquids splash instead of blob.

Note this is already a custom GPU solver, entirely separate from Jolt. Jolt never sees particles; it handles only debris rigidbodies.

Three kernels, double-buffered

KernelThreadsRole
args1 / args21Write indirect dispatch + draw args
integrate64/wg, indirectGravity, path-sample, propose reinsert
resolve64/wg, indirectSettle claims, rejoin grid

Particles ping-pong between two pages; integrate reads page p and appends survivors to page 1−p, so death is simply "not appended" — no compaction pass needed.

Sub-voxel integration

Positions are 24.8 fixed-point. Each tick the flight path is sampled at ≤ half-voxel intervals (n = max(1, (maxComponent + 127) / 128)), so fast particles cannot tunnel through thin walls. On hitting a blocking cell, the particle proposes reinsertion at the last empty position.

Deterministic conflict resolution

Many particles may target one cell. Rather than first-come-CAS — which would be scheduling-dependent — each writes atomicMax of a priority value into a claim hash, and resolve admits only the particle whose priority equals the winning value. atomicMax is order-independent: the same set of contenders always yields the same winner, preserving bit-determinism.

Computation

capacity   262,144 particles (32 B each = 8 MB × 2 pages)
claim hash 262,144 u32 (1 MB)
threads    2 × ceil(live / 64) workgroups × 64
at cap     ~524k thread-launches/tick
Limits

Overflow is silently dropped: append increments the count atomically but discards writes past capacity, so an over-cap frame loses particles rather than degrading gracefully. The claim hash can alias — two distant cells sharing a slot means one particle loses a contest it should have won, which is rare, deterministic, and self-correcting. Buried particles rise one voxel per tick, which can look sluggish under heavy burial.

▶ gpu Occupancy + pick Per-chunk emptiness flags for render skipping; cursor raycast dirty-only

Recomputes per-chunk occupancy — whether a chunk holds any voxels — which the renderer uses for empty-space skipping and the CPU uses for collision routing. One workgroup of 64 threads per chunk, each thread folding 64 cells.

Critically, this runs over the compacted next-tick dirty list, not all 4,096 chunks. A full-world occupancy scan happens only on hash ticks. This was a deliberate optimization: a settled world updates ~4 chunks instead of 4,096.

sim_pick.wgsl rides along as a single-thread dispatch, raycasting the cursor ray through the grid for the brush preview.

Limits

Occupancy is binary per chunk — a chunk holding one voxel is as "occupied" as a solid one, so empty-space skipping is coarse at 16³ granularity. Pick is one thread and therefore latency-bound rather than throughput-bound; it costs a full serial DDA walk.

▶ transfer Async readback 3-slot ring, one tick latent — the CPU's window into GPU state ≤1 MB/tick

The architecture stands or falls on this stage (DESIGN.md risk #2). The player controller and physics need to know what voxels are where, but the world lives in device memory and a synchronous read would stall the pipeline.

The answer is a 3-slot ring buffer with mapAsync, deliberately one tick latent. At 30 Hz, one tick of latency on terrain collision is imperceptible. If every slot is still in flight, the tick skips its copies rather than blocking — the sim never waits on the CPU.

kFetchPerTick = 64 is chosen precisely to hold total traffic at the ~1 MB/tick ceiling — about 30 MB/s, trivial for PCIe.

Limits

The mirror covers only 3×3×3 chunks (48³ voxels) around the player; queries outside it return Unknown, so anything needing distant voxel data must request a fetch and wait a tick. Under sustained demand above 64 chunks/tick the fetch queue grows unboundedly — island detection must therefore bound its own region requests. The one sanctioned synchronous read is the selftest's hash.

▶ cpu Islands, debris, and Jolt Bounded flood fill → marching cubes → rigidbodies ≤200 bodies

Destroying support must let disconnected terrain fall. CA rules only see immediate neighbors, so connectivity needs an explicit pass. This is DESIGN.md's risk #1 — flagged by the one team who has shipped it as "hardest, not completely solved."

Pipeline

  1. A destruction event registers an expanded voxel box.
  2. The region is fetched asynchronously through the readback ring.
  3. Bounded 6-connected flood fill runs outward. Exceeding ~32,000 voxels aborts and declares "not an island."
  4. Islands leave the grid via exact-cell ops and become Jolt bodies with greedy-merged box compounds; mass sums per-voxel material density.
  5. Islands under 8 voxels crumble to their powder form and stay in the CA.

The 32k bound is a design decision as much as a performance one. An unbounded check could collapse an entire dungeon level — Noita's lesson that "the world is simulated too much" kills level design.

Why Jolt, and what it actually does

Jolt handles ≤200 debris bodies and static terrain patches — nothing else. At that count, narrow-phase resolution is microseconds of a 33 ms tick, so a custom solver would optimize a non-bottleneck. The expensive parts of this stage — flood fill, marching cubes, readback — are all custom code already.

Jolt is built with CROSS_PLATFORM_DETERMINISTIC, keeping lockstep viable. But bodies are CPU float state deliberately outside the hashed grid domain: they re-enter the world only through the op stream, so the grid replays exactly regardless of solver behavior.

Limits

Large floating sections can survive the bounded fill — a known, accepted flaw. Body count caps at 200 and voxel instances at 262,144; excess bodies are culled. Damaging a body means destroying and rebuilding it, losing solver state. Terrain collision meshes are cached per chunk and rebuilt on dirty, so a chunk churning every tick rebuilds its mesh every tick.

▶ render Raymarched rendering DDA through the voxel grid — no meshing, reads sim buffers directly 2.66 ms @1080p

Terrain geometry changes every tick, so meshing churn would dominate. Instead a fullscreen pass raymarches the voxel grid directly, DDA-stepping through chunks and using occupancy flags for empty-space skipping. The sim already lives in GPU memory, so the renderer reads it at zero upload cost.

Passes

  • raymarch — fullscreen terrain; primary ray plus a secondary ray for sun shadows.
  • particleDraw — instanced cubes, 36 verts each, indirect off the GPU-written count.
  • spriteDraw — CPU-authored markers, ≤64.
  • bodyDraw — debris voxel instances transformed by body quaternion.

Shadows nearly double frame cost — the secondary ray roughly doubles traversal work. This is the single largest render lever.

Floats are correct here. The determinism rule binds only values that influence voxel state; rendering is a pure consumer.

Limits

Cost scales with screen pixels and traversal depth, not world activity — so unlike the sim, a settled world renders no cheaper. Empty-space skipping is chunk-granular, making sparse scattered voxels the worst case. There is no LOD: distant geometry costs the same per-step as near geometry, which is the main obstacle to a larger view distance.

Cross-cutting invariants

These hold across every stage above. Each is cheap to maintain now and near-impossible to retrofit.

▶ invariant Bit-determinism Same seed + tick + inputs → same hash, on every GPU hash 3dbdf3c1

The property that keeps lockstep multiplayer and replay debugging viable. A per-tick world hash is both the verification tool and, in multiplayer, the desync detector.

Rules

  • Integer-only sim math. No float may influence voxel state; compilers diverge on FMA contraction and fast-math.
  • Stateless counter RNG — hash3(seed, tick, idx), never a stateful stream.
  • No scheduling-dependent outcomes. No CAS claims, no subgroup ops, no order-dependent reductions. Order-independent atomics (atomicMax for particle claims, atomicAdd for list append) are fine — the outcome does not depend on arrival order.
  • Write reach ≤1 cell, or the color-lattice disjointness proof collapses.

Verified by --selftest, which runs the sim twice and compares hashes over 200 ticks including explosions and particle activity.

Open risk

Determinism is currently verified on one vendor only (RTX 3060 Ti). Cross-vendor validation — DESIGN.md risk #3 — remains open, and it is the risk most likely to invalidate the lockstep plan.

▶ invariant Sleeping Cost scales with activity, not world size 4 / 4096 settled

"Sleeping is the product." Every system needs a costs-nothing-when-idle state. A settled 256³ world holds 16.7M voxels and simulates 4 chunks — 0.1% of the world.

Mechanism

Anything that changes marks its chunk dirty. A voxel moving across a chunk boundary must also mark the neighbor. A chunk with no movement and no active reactions clears its flag and sleeps. Compaction then reduces the active set to an indirect dispatch count.

Liquids required specific care: fullness-1 films never spread, so pools settle flat and sleep rather than jittering forever at the surface.

The subcritical-growth trap

Any reaction whose expected offspring per tick is ≥1 grows without bound, so its chunks never sleep and the world never settles. This looks exactly like a performance regression but is a content bug in reactions.json. The selftest guards it: a settled world must hold under 32 active chunks.

Live telemetry (planned)

This page is built to become a measurement device. The bar at the top connects to the running simulation; each stage's cost chip then shows live values and reveals a sparkline of its recent history.

The wire format is one JSON object per tick over a WebSocket. Stage keys match the data-stage attributes on this page, so adding a stage to the engine needs no page changes beyond a new <details> block:
